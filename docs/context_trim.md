# 上下文裁剪

会话历史会一直增长。每轮都带工具调用时，消息条数增长很快，工具返回的 JSON 也可能很长。
如果把全部历史直接发给模型，最终会撞上上下文上限，或者让每轮延迟和费用不断上升。

本模块决定「哪些消息进入本次模型调用」，**不决定「保存什么」**：
`chat_threads.messages_json` 仍然保存完整历史，恢复会话和事后审计都不受影响。

## 裁剪策略

1. **始终保留 system 消息**，并把它放在第一位；
2. **保留最近的若干条消息**，默认窗口上限 24 条；
3. **裁剪边界向前对齐**：如果窗口的第一条是 `tool` 消息，就把它对应的
   `assistant(tool_calls)` 一并带上；
4. **单条工具结果限长**，默认 1200 字符，超出部分截断并追加 `…[内容已截断]`；
5. 被丢掉的部分不静默消失：在 system 消息末尾追加一句
   「更早的 N 条对话记录已省略」，让模型知道自己看到的是不完整历史。

## 为什么边界对齐是硬约束

OpenAI 兼容接口要求每条 `tool` 消息都能找到发出它的 `tool_call`。
如果裁剪把 `assistant(tool_calls)` 切掉、只留下 `tool`，接口返回的是 **400**，
而不是降级或忽略——整轮对话直接失败。

所以对齐优先于窗口上限：为了不产生孤立的 `tool` 消息，
实际窗口可能比 `max_messages` 多出一次工具调用对应的消息（通常 1 条，批量调用时更多）。
这是有意的取舍，`max_messages` 是目标值而非严格上界。

## 为什么不调用模型做摘要

摘要需要额外一次模型调用：增加延迟和费用，且结果不确定，
同一段历史两次摘要可能不同，破坏评测的可复现性。当前用固定占位说明代替。

## 配置

常量位于 `app/harness/context.py`：

| 常量 | 默认值 | 含义 |
|---|---|---|
| `MAX_CONTEXT_MESSAGES` | 24 | 单次模型调用的消息条数目标 |
| `MAX_TOOL_RESULT_CHARS` | 1200 | 单条工具结果的最大字符数 |

当前是模块常量而非环境变量：改动需要重新部署，避免线上被临时调参掩盖问题。
后续接入配置模块时再迁移。

## 运行与验收

```powershell
conda run -n retail-agent python -m pytest tests/test_context_trim.py -q
```

覆盖的检查：

- 短历史原样返回；
- 长历史被裁剪到目标条数附近；
- system 消息保留且只有一条，并带有省略说明；
- 在 6 到 29 的各种窗口上限下，都不产生孤立的 `tool` 消息；
- 最近两条消息完整保留；
- 超长工具结果被截断并标记；
- 传入的列表不被修改（持久化拿到的仍是完整历史）。

端到端观察：连续对话若干轮后，`data/traces.jsonl` 会出现 `context.trimmed` 事件，
包含 `before`、`after`、`dropped`、`truncated` 四个字段。

## 当前限制

- 不区分消息重要性，只按时间顺序保留最近部分；早期轮次里的事实会离开窗口，
  需要时由 Agent 重新查询工具，而不是依赖记忆。
- 不做工具结果的语义压缩，只按字符截断。
- 摘要是固定文案，不含被省略内容的关键信息。
